# Robosumo RL — версія 0.1 (2026-10-27)

Перша завершена версія: нейромережева політика керування для 3-кг робота сумо, натренована з нуля
з підкріпленням (RL) у симуляторі, спершу у швидкому 2D, потім у 3D з геометрією з CAD. На залізі ще не запускалась.

Чекпоінт версії: `results/m5/ckpt_final.pt` (interface v2). Git-тег: `v0.1`.

---

## 1. Задача і робот

- Робот: 3 кг, 190×199×99 мм, клин (лопата) спереду, 2 колеса Ø70 мм позаду, колія 149 мм, ЦМ ~2 см попереду осі.
  Геометрія — з Fusion (`sim3d/assets/robot_mdl.step`). Ця геометрія взяла 2-ге місце на всеукраїнських змаганнях 2026.
- Привід: 2 мотори JGY-370 з черв'ячним редуктором 1:40 (самогальмування: стоячий мотор тримає колесо), 4S LiPo.
- Сенсори, які є зараз: 3× ІЧ-датчики суперника E18-D80NK (0°, ±15°, лише «бачу / не бачу»), 4 датчики краю рингу
  в кутах, напруга батареї. Енкодерів і IMU поки немає.
- Суперник: такий самий робот із класичною скриптовою логікою (скінченний автомат, FSM) — кілька стилів:
  aggressive, cautious_edge_waiter, spinner, random_walker, плюс нерухома ціль.
- Ринг: Ø1.6 м з чорною окантовкою 5 см. Програє той, чий центр мас виїхав за край. Таймаут 20 с → нічия.
- Цільовий мікроконтролер: ESP32 (мінімум) або STM32 (бажано); мережа рахується на ньому 100 разів на секунду.

## 2. Як влаштована система

```
 robot_spec.yaml ──► симулятор (тисячі матчів паралельно на GPU) ──► PPO-тренер ──► чекпоінт
   (усі числа         2D: свій PyTorch (M0–M4)                       актор + критик
    про залізо)       3D: MuJoCo Warp + CAD (M5)                         │
                                                                         ▼
                       на МК піде лише актор:  сенсори → шар прошивки → мережа → шар прошивки → мотори
```

- **Один файл параметрів** (`robot_spec.yaml`): маса, мотори, шини, сенсори, затримки, ринг, діапазони
  рандомізації. У коді немає магічних чисел — змінив залізо в spec, і все підхопилось.
- **Симулятор на GPU**, повністю батчевий: 16 384 матчі одночасно.
  - 2D (`sumo/`): свій rigid-body, модель мотора τ–ω з мертвою зоною і затримкою, черв'як, тертя шин,
    контакти корпусів, модель піддівання клином. ~430k кроків/с тренування.
  - 3D (`sim3d/`): MuJoCo Warp; корпус і лопата з CAD (бокси + пластини по профілю лопати + гостра кромка),
    колеса-циліндри, тертя шин з різницею кочення/ковзання, ІЧ — справжні промені. ~170–190k кроків/с тренування.
  - Сенсори з шумом, затримками, хибними спрацюваннями і засвіткою від ІЧ суперника.
- **Шар прошивки** (`sumo/firmware.py`) — той самий код буде в C на роботі: обмеження швидкості зміни команди
  (slew), компенсація мертвої зони мотора, «пам'ять» сенсорів (скільки часу тому кожен датчик спрацьовував).
- **Тренер**: PPO (свій, у стилі CleanRL) з асиметричним актором-критиком, curriculum і self-play лігою.

## 3. Архітектура політики (те, що піде на МК)

**Вхід — 151 число**, усе доступне на реальному МК:
- 7 «кадрів» сенсорів: зараз і 1, 2, 4, 8, 16, 32 цикли тому (до 320 мс назад). У кожному кадрі 20 значень:
  3 ІЧ, 4 датчики краю, попередня команда (2), батарея, і 10 резервних слотів під бокові ІЧ, енкодери, IMU
  та прапорці їх наявності (зараз нулі; ваги для них стартують з нуля). 7 × 20 = 140.
- 11 значень пам'яті прошивки: скільки часу тому спрацьовував кожен ІЧ (3 + 2 резервні) і кожен датчик краю (4),
  з якого боку востаннє бачили суперника, як довго вже триває штовхання.

**Мережа**: нормалізація входів (статистики заморожені в чекпоінті) → 64 → 64 (ReLU) → 2 (tanh).
14 020 параметрів (~56 КБ у float32) — дрібниця для ESP32/STM32.

**Вихід — 2 числа** у [−1, 1]: частка максимальної тяги лівого і правого мотора. Далі шар прошивки
(slew → компенсація мертвої зони) → ШІМ.

**Критик** (тільки в симуляторі, на МК не йде): ті самі 151 вхід + 113 «привілейованих» — точні позиції і
швидкості обох роботів, стан FSM суперника, усі випадкові параметри заліза. Мережа 256-256 (ELU). Він допомагає
вчитися, бачачи те, чого робот не бачить.

**Інтерфейс заморожено** (`sumo/interface.py`, версія 2): склад, порядок і масштаби входів, сенс виходу і розмір
мережі фіксовані. Тому будь-який чекпоінт можна дотреновувати після зміни заліза, не починаючи з нуля.

## 4. Нагорода

- +10 перемога, −10 поразка, нічия −1 (M3–M4) / −4 (M5).
- На початку (M3) — підказки: за наближення до суперника і за відсування його від центру; повністю згасли до 400M кроків.
  Далі тільки результат матчу + маленький штраф за ривки команди.

## 5. Етапи тренування

Один «крок» = 10 мс одного матчу. 16 384 матчі паралельно → 1 млрд кроків ≈ 1–1.5 год на RTX 3070.

| Етап | Де | Кроків | Що відбувалось | Результат |
|---|---|---|---|---|
| **M3** RL v1 | 2D | 500M | З нуля. Curriculum: нерухома ціль → random_walker → усі FSM. Підказки в нагороді згасають. | 83–97% перемог проти FSM |
| Interface v1 → v2 | — | — | Заморожено інтерфейс; додано пам'ять (кадри до 320 мс) і пам'ять прошивки | ваги M3 перенесено без втрати |
| **M4** ліга (1-ша спроба) | 2D | 2.74B | Self-play з пулом старих версій. Зациклилось «камінь-ножиці-папір» (без пам'яті й з багом дублювання кадрів) | відкинуто, стилі стали якорями |
| **M4** ліга v3 | 2D | 2B | Self-play з PFSP (частіше з тими, кому програє), постійні якорі різних стилів, FSM | Elo 1422 (M3) → 1555; проти FSM 91–96% |
| 3D-тест | 3D | 300M | Перенос M4 у 3D без змін інтерфейсу | одразу 41–57%, після 300M 64–72% проти FSM |
| **M5** робастність, прогін 1 | 3D | 400M | Рандомізація заліза (див. нижче) | ~55–70%, багато нічиїх → знайдено артефакт лопати |
| M5, прогін 2 | 3D | 400M | Виправлена лопата (гостра кромка) | плато ~50% → знайдено проблему тертя шин |
| M5, прогін 3 | 3D | 600M | Тертя шин з різницею кочення/ковзання | фінал v0.1 (нижче) |

Лінія фінальної політики: M3 500M → M4 v3 2B → 3D 300M → M5 400M + 400M + 600M ≈ **4.2 млрд кроків**.
Разом з відкинутими прогонами натреновано ~7 млрд кроків.

**Рандомізація в M5** (кожен робот у кожному матчі отримує своє залізо): момент і оберти моторів ×0.7–1.3,
сила 0.9–1.1, розбіжність лівий/правий, напруга батареї, маса 2.85–3.0 кг, положення ЦМ 0.5–3.5 см від осі і висота
3–5 см, зчеплення шин 0.5–1.2 і ковзання ×0.6–0.9, тертя лопати, гострота кромки 0–2 мм, затримки сенсорів,
частота циклу 80–120 Гц, бокові/резервні сенсори є або нема. Мета — політика, яка не залежить від точних чисел заліза.

## 6. Результати v0.1

**3D, рандомізоване залізо, проти FSM** (1024 матчі на суперника, перемоги / нічиї / поразки):

| суперник | v0.1 |
|---|---|
| нерухома ціль | 47 / 52 / 0 |
| aggressive | 61 / 36 / 3 |
| cautious_edge_waiter | 55 / 42 / 3 |
| spinner | 50 / 45 / 4 |
| random_walker | 63 / 35 / 2 |

Програє рідко (0–4%), але половина матчів — нічия: штовхає правильно, проте не встигає виштовхати за 20 с.

**Екстремальне залізо** (обидва роботи однакові, номінал 64% перемог):
зчеплення μ 0.5 — 65%; короткий ІЧ 0.6 м — 64%; великі затримки + 80 Гц — 61%;
легкий + ЦМ далеко вперед — 43%; слабкі мотори — 33%; найгірший випадок — 31%. Поразок всюди 1–2%:
слабший привід = повільніше штовхання = більше нічиїх, а не програші.

## 7. Що знайшли по дорозі (корисне для інших)

- **Переваги «слота 0»**: рівні випадки в моделі клина і старт пліч-о-пліч завжди віддавали перемогу першому роботу.
  RL це миттєво знаходить — тепер є тести на дзеркальну симетрію.
- **Ліга без пам'яті зациклюється**: реактивна політика (30 мс історії) у self-play ходила по колу стилів замість
  прогресу. Лікування: пам'ять (320 мс + лічильники прошивки), постійні якорі, пропорційна модель клина.
- **Апроксимація лопати в 3D**: тонка пластина, піднята над рингом, мала тупий торець на вістрі, який завжди
  підкидав того, хто наїжджав; той лягав на хвіст і крутив колесами в повітрі. Замінено гострою кромкою.
- **MuJoCo не розрізняє тертя кочення і ковзання**: штовхач не міг здвинути однакового робота на заблокованих
  черв'яком колесах. Додано тертя, що залежить від проковзування колеса.
- **Інженерне**: батчеві скидання без синхронізації CPU-GPU, eval одним батчем, атомарні чекпоінти кожні 10M кроків
  (вимкнення світла не страшне), захист від NaN у 3D, eval шматками під 8 GB відеопам'яті.

## 8. Обмеження v0.1 і що далі

- Не перевірено на залізі; параметри моторів, зчеплення, ковзання шин, висоти ЦМ — оцінки, їх треба заміряти.
- Нічиї на таймауті в 3D — головне обмеження якості. Гіпотеза: горизонт PPO (gamma 0.995) замалий для клінчів по 10+ с.
- Тест «змінив колеса на Ø80 → дотренував швидше, ніж з нуля» не робили (пропустили); регресійний набір після M5 не запускали.
- Наступні етапи: експорт мережі в C і перевірка, що C на ПК дає ті самі виходи (M7); прошивка з шаром безпеки
  (рефлекс краю, watchdog) (M8); логи з реального робота → уточнення симулятора → дотренування (M9).

## 9. Як відтворити / подивитись

```bash
uv sync && uv run pytest                                        # 81 тест
uv run python -m train.eval --ckpt results/m5/ckpt_final.pt --sim 3d
uv run python -m train.eval --ckpt results/m5/ckpt_final.pt --extreme configs/eval_extreme.yaml --sim 3d
uv run python -m sim3d.render3d --ckpt results/m5/ckpt_final.pt --opponent aggressive --out v01.mp4
```
Детальніше: `PLAN.md` (етапи), `STATUS.md` (стан), `PROGRESS.md` (журнал знахідок), `robot_spec.yaml` (параметри).
