# План: RL-політика для робосумо 3 кг

Мета: натренована int8 MLP, що працює на Arduino Nano поверх safety-шару, і цикл дотренування через логи з реального заліза.
Параметри: `robot_spec.yaml`. Правила роботи: `CLAUDE.md`.

---

## M0. Сетап
- Репо, `uv`, PyTorch з CUDA, pytest, tensorboard, ffmpeg.
- `sumo/config.py`: читання `robot_spec.yaml` і семплінг randomization у батч-тензори `[num_envs, ...]`.

**Готово:** `torch.cuda.is_available()`, конфіг читається, тест на семплінг діапазонів проходить.

---

## M1. Фізика 2D (батчево на GPU)
Стан кожного робота: `x, y, θ, vx, vy, ω` + швидкості коліс. Обидва роботи в одному тензорі.

- **Мотор:** τ = u·(V/V_nom)·τ_stall − (τ_stall/ω₀)·ω, обмеження струму, deadband, перша-порядкова затримка.
- **Черв'як (самогальмування):** зовнішні сили не провертають колесо проти мотора; при u=0 колесо блокується.
  Підхід: швидкість колеса керується тільки мотором, а різниця з реальною швидкістю точки контакту йде в ковзання шини.
- **Шина:** сила = μ·N·tanh(slip/s₀) (згладжений Кулон). N рахується з положення ЦМ між віссю і точкою опори лопати.
- **Лопата:** тертя ковзання по рингу, μ з randomization.
- **Контакт роботів:** прямокутники (SAT), penalty spring-damper + тертя між корпусами.
- **Клин (опційно, v2):** при контакті передом частина ваги суперника знімається з його коліс (`lift_fraction` у randomization).
- **Вильот:** ЦМ за межею рингу → поразка.
- Інтегрування: напівнеявний Ейлер, dt = 2 мс, керування раз на 10 мс.

**Тести-інваріанти:**
- без команд робот стоїть; симетричні команди → їде прямо;
- швидкість на рівному виходить на ~0.78 м/с (з поправкою на втрати);
- повний газ в упор у стіну → колеса буксують, а не «штовхають» більше за μ·N;
- зовнішня сила на заблокований робот не крутить колеса;
- 4096 середовищ крутяться ≥ 50k кроків/с на 3070.

**Готово:** тести проходять, відео руху і зіткнень виглядає фізично правдоподібно.

## M2. Сенсори, суперник, правила матчу
- **E18-D80NK:** рейкаст з конусом проти прямокутника суперника, дальність з randomization, затримка,
  false negative/positive, кросток від ІЧ суперника, вихід 0/1.
- **Line-сенсори:** точка в зоні білої лінії → 1, із затримкою.
- **Battery ADC:** нормована напруга.
- **Хардкод-FSM** (векторизований): SEARCH → ATTACK → ESCAPE, варіанти aggressive / cautious / spinner / random,
  параметри рандомізуються. Працює на тих самих сенсорах і фізиці.
- **Матч:** стартові режими зі spec, таймаут 20 с, перемога / поразка / нічия.

**Готово:** FSM проти FSM дає правдоподібні бої на відео; aggressive б'є random_walker у >80% матчів.

## M3. RL v1
- **Актор (на Nano):** вхід = [3 ІЧ, 4 лінії, попередня дія (2), батарея] × frame stack 3 → MLP 32-32 → 2 (tanh).
- **Критик (тільки в симі):** привілейований стан обох роботів + параметри randomization, MLP 256-256.
- **Дії:** [u_left, u_right] з slew limit (як у прошивці).
- **Reward:** +10 перемога, −10 поразка, −1 нічия; невеликий шейпінг: наближення до суперника,
  відсування суперника від центру, штраф за ривки дії. Шейпінг вимикається поступово.
- **PPO:** 2048-4096 середовищ, GAE, normalizing обсервацій (статистики фіксуються для експорту).
- **Курикулум:** нерухома ціль → random_walker → FSM-варіанти.

**Готово:** політика стабільно б'є всі FSM-варіанти (>70% win-rate), відео без очевидних експлойтів.

---

## M4. Self-play і ліга
- Пул заморожених версій політики + усі FSM. Семплінг суперників з пріоритетом тих, кому програємо.
- `eval.py`: матриця win-rate, Elo, регресійний набір.

**Готово:** нові версії не програють FSM, Elo росте, політика не «забуває» старих суперників.

---

## M5. Робастність (domain randomization)
- Увімкнути всі `*_rand` зі spec, рандом частоти циклу, затримки, розсинхрон моторів.
- Окремий eval на «екстремальних» параметрах (слабкі мотори, мало зчеплення, короткий ІЧ).

**Готово:** падіння win-rate на екстремальних параметрах не більше ~15% від номінальних.

---

## M6. Експорт на Arduino Nano
- `quantize.py`: int8 ваги, per-layer скейли, int32 акумулятор, ReLU, нормалізація входів вшита в перший шар.
- `gen_header.py` → `firmware/policy_weights.h` (PROGMEM).
- **Паритет:** однакові вхідні вектори → вихід PyTorch (int8-симуляція) == C на ПК == Nano (через Serial).
- Тренувальний eval з квантованою політикою (щоб квантування не вбило поведінку).
- Заміряти час інференсу на Nano через `micros()`.

**Готово:** паритет у межах ±1 LSB, інференс вкладається в бюджет циклу (ціль < 3 мс при 100 Гц).

---

## M7. Прошивка
Шари, у порядку виконання за цикл:
1. Читання сенсорів (E18 цифрові, лінії, ADC батареї).
2. Фільтри / frame stack (та сама логіка, що в симі).
3. Політика (int8).
4. **Safety:** рефлекс краю (хардкод назад + розворот, перебиває політику), watchdog
   (довго крутиться без контакту → FSM-фолбек), обмеження часу клінчу (нагрів 12-В моторів на 16 В).
5. Slew limit, deadband-компенсація, калібрувальні коефіцієнти лівий/правий.
6. PWM.
- Старт: 5-секундна затримка за правилами.
- Логування: бінарні пакети по Serial (1 Мбод) на ноут або логер (OpenLog / ESP32).

**Готово:** робот виконує політику, рефлекс краю спрацьовує раніше вильоту на макс. швидкості, логи пишуться.

## M8. Sim2real цикл
1. Заміряти: обороти без навантаження і струм зупинки на 16 В, розподіл ваги (ваги під колесами),
   швидкість на прямій, час розвороту на 180°, гальмівний шлях.
2. Підігнати параметри spec (system identification), звузити діапазони randomization навколо реальних.
3. Реальні бої проти FSM-робота з логами.
4. **Actuator net (коли будуть енкодери):** маленька мережа, натренована supervised на логах
   «PWM + напруга + стан → реальна швидкість колеса». Замінює ручну модель мотора в симі.
5. Перетренування в оновленому симі → експорт → прошивка → бої. Повторювати.

Дотренування прямо на залізі тільки обмежене: residual-корекція або останній шар з малим learning rate,
safety-шар лишається завжди.

**Готово:** політика на реальному ринзі б'є FSM-робота частіше, ніж FSM б'є сам себе.

## M9 (опційно). 3D у MuJoCo Warp
Коли 2D впреться в стелю (клин vs клин, підйом суперника, нерівний ринг): той самий інтерфейс obs/action,
перенесення фізики в MJCF, тренування через MuJoCo Warp / mjlab.

## Рекомендовані апгрейди заліза
- **Енкодери на моторах:** без них system ID і actuator net дуже обмежені.
- **STM32 замість Nano:** зніме обмеження на розмір мережі, пам'ять кадрів і частоту.
- Зсув ваги назад, щоб більше притиснути колеса (зчеплення зараз основне обмеження).
